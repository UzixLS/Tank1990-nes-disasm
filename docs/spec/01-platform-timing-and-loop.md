# Платформа, время и главный цикл

## Целевая система

Оригинал является программой для NTSC Famicom/NES в формате iNES:

| Параметр | Значение |
|---|---|
| mapper | 0, NROM-256 |
| PRG ROM | 32 КиБ |
| CHR ROM | 8 КиБ |
| mirroring | horizontal |
| battery RAM | нет |
| спрайты | 8×16 |
| таблица паттернов фона | `0x1000` |
| таблица паттернов спрайтов | определяется младшим битом номера 8×16-спрайта |
| обычный `PPUCTRL` | `0xB0` |
| обычный `PPUMASK` | `0x1E` |

Это подтверждено заголовком и инициализацией [ROM]. Устройство NROM и ограничения PPU описаны в [NESdev NROM](https://www.nesdev.org/wiki/NROM) и [NESdev PPU](https://www.nesdev.org/wiki/PPU) [REF].

Современная реализация НЕ ДОЛЖНА эмулировать NES целиком. Она ДОЛЖНА использовать логическое разрешение 256×240, целочисленные координаты и фиксированный логический такт. Рекомендуемый такт — 60.0988 Гц, то есть NTSC NES; 60 Гц приемлемы для игровой совместимости. Источник частоты: [NESdev cycle reference](https://www.nesdev.org/wiki/Cycle_reference_chart) [REF].

## Временная модель

Есть два беззнаковых счётчика:

```text
frameCounter = (frameCounter + 1) mod 256        каждый NMI
if frameCounter mod 64 == 0:
    slowFrameCounter = (slowFrameCounter + 1) mod 256
```

Следствия:

- бит 4 `frameCounter` даёт период мигания 32 кадра: 16 невидимых и 16 видимых;
- `slowFrameCounter` меняется примерно каждые 1.065 секунды;
- сравнения с ним не являются секундомером с насыщением: после 255 он возвращается к нулю;
- многие вероятности зависят от младших битов `frameCounter`, поэтому логику нельзя запускать с переменным шагом.

Таймеры явно делятся на три класса:

1. уменьшаемые каждый логический такт;
2. уменьшаемые только в обслуживаемый такт конкретного объекта;
3. уменьшаемые при изменении `slowFrameCounter`.

В главах ниже класс таймера указан возле его определения.

## Работа на вертикальном гашении

Для точной совместимости один NMI выполняет действия в следующем порядке [ROM]:

1. копирует теневой OAM в PPU через DMA;
2. отправляет накопленную очередь изменений фона;
3. при необходимости загружает палитру;
4. устанавливает `PPUCTRL`, scroll и `PPUMASK`;
5. опрашивает оба контроллера и вычисляет `held`/`pressed`;
6. завершает текущий OAM-кадр и меняет направление выделения спрайтов;
7. обновляет звуковой движок;
8. увеличивает `frameCounter`;
9. на каждом кратном 64 кадре увеличивает `slowFrameCounter`.

Игровая логика работает между NMI. Современная реализация может объединить этапы, но должна считать, что введённые на NMI кнопки доступны следующему игровому такту, а визуальные данные, подготовленные игровым тактом, выводятся на следующем NMI.

## Состояние контроллера

Для каждого игрока хранится:

```text
held    = текущая маска кнопок
pressed = held AND NOT previousHeld
previousHeld = held
```

Используются стандартные кнопки NES: `A`, `B`, `Select`, `Start`, `Up`, `Down`, `Left`, `Right`. Если несколько направлений удерживаются одновременно, игровой приоритет равен:

```text
Right > Left > Down > Up
```

Это относится к управлению танком и редактором карт [ROM]. Диагонального движения нет.

## Нормативный такт боя

Активный бой ДОЛЖЕН обновляться в таком порядке [ROM]:

```text
1  отметить занятые танками клетки по позициям начала такта
2  обработать ввод игроков
3  обновить состояния и движение танков
4  снять временные отметки занятости
5  сдвинуть и анимировать существующие снаряды
6  обновить эффект разрушенной базы
7  обновить визуальные эффекты щита игроков
8  создать новые выстрелы игроков
9  создать новые выстрелы противников
10 создать ожидающий танк противника, если разрешено
11 разрешить столкновения снарядов с местностью
12 разрешить столкновения снаряд-снаряд
13 разрешить столкновения снаряд-танк и снаряд-база
14 обработать подбор бонуса
15 обновить движущийся объект GAME OVER
16 выбрать звук движения игроков
17 обновить показ жизней
18 выполнить расширения Tank 1990
```

После логики отрисовываются бонус, снаряды, танки и наложения. Порядок принципиален. Например, выстрел игрока, созданный на шаге 8, ещё не сдвигается на шаге 5, но уже может столкнуться на шагах 11–13 этого же такта.

## Пауза

Нажатие `Start` в бою переключает паузу. Переключение выполняется после подготовки текущего кадра, поэтому кадр на границе использует предыдущее состояние.

Во время паузы:

- пункты 1–18 не выполняются;
- кадр и медленный счётчик продолжают идти;
- контроллеры продолжают опрашиваться;
- бонус, снаряды и танки продолжают рисоваться в неподвижных позициях;
- слово `PAUSE` мигает 16 кадров из каждых 32;
- звуковой движок заглушает обычные каналы, оставляя только служебный поток паузы.

Пауза не замораживает время внешнего `frameCounter`, но замораживает все игровые таймеры, которые уменьшаются только в боевом такте.

## Генератор псевдослучайных чисел

Для покадровой совместимости используется 8-битный генератор с обратной связью через нулевую страницу [ROM]. Один вызов вычисляет:

```text
product = 7 * randomState
low = product mod 256
carry = floor(product / 256)

partial = low + slowFrameCounter
carry2 = floor(partial / 256)

randomIndex = (randomIndex + 1) mod 256
randomState = (partial + zeroPage[randomIndex] + carry2) mod 256
return randomState
```

`carry` от умножения не прибавляется: умножение реализовано с сохранением только младшего байта. `zeroPage` означает реальные текущие 256 байт рабочей памяти оригинала, поэтому случайность зависит от состояния игры и точного числа вызовов.

Независимая реализация, которой не нужны совпадающие replay, МОЖЕТ заменить генератор детерминированным 8-битным PRNG. Она всё равно ДОЛЖНА:

- делать отдельный вызов в каждой точке, описанной далее;
- не заменять проверки младших битов вероятностями с плавающей точкой;
- позволять задавать seed для тестов.

## Переполнение и сравнения

Точная модель использует 8-битную арифметику:

- координаты и обычные таймеры переполняются по модулю 256;
- расстояние для попадания сначала вычитается по модулю 256, затем трактуется как знаковое и берётся абсолютная величина;
- счёт хранится семью десятичными цифрами и переполняется после 9 999 999;
- номер этапа является байтом; автоматическое продолжение превращает `0xFF` в `1`.

Игровая копия может применять более широкие типы, но должна явно воспроизводить эти границы там, где они наблюдаемы.
