# Tank 1990 (Ch) — исходный код

Проект восстанавливает исходный код и ассеты NES-игры `Tank 1990 (Ch).nes`.
Результат собирается ca65/ld65 и побайтово совпадает с исходным образом.

## Сборка

Требуются GNU Make 4.3+, cc65 2.19 и Python 3.12. Сторонние Python-пакеты не
используются. Локальные пути к инструментам можно переопределить в
игнорируемом `Makefile.local`; заготовка — `Makefile.local.example`.

```sh
make all
make test-tools
make verify
make test
make audit
make level-screenshots
```

Собранный образ находится в `build/tank1990-ch.nes`. `make all` и
`make test-tools` не читают исходный NES-файл: вторая цель проверяет
только общие round-trip/валидационные свойства конвертеров.

`make verify`, `make test-assets`, полная `make test` и `make audit`
предназначены для byte-exact исходного восстановления и читают
`Tank 1990 (Ch).nes`. Цель `verify` сравнивает сборку с оригиналом и
проверяет SHA-256
`ec453e7e3cc1d49d11d5860ced7f9e1235e2c7d33927bd6073b631754dc08dbb`.

`make audit` проверяет разметку всех PRG-байтов, адресные метки, границы прямых
переходов и таблицы обработчиков; сверяет все 142 записи карт и отдельно
экспортирует 71 скрытую карту в `build/hidden-levels/`. Файл `index.csv` связывает
экспорт с исходным `.map`, CPU-адресом и смещением в ROM. Отчёты —
`build/disassembly-audit.json` и `build/level-audit.json`; заголовок, PRG- и
CHR-банки извлекаются в `build/original/`. Это временные результаты, не исходники.
Отдельные цели — `make audit-levels` и `make audit-disassembly`.

`make test-assets` также исполняет байты загрузчика карт в ограниченном
6502-исполнителе: проверяет 3570 комбинаций варианта/этапа, демонстрационный
режим и распаковку 214 окон. PPU/NMI заменены перехватами вызовов; эта проверка
не эмулирует игру целиком. Подробности — [аудит ROM и уровней](docs/audit.md).

## Редактирование ассетов

`make level-screenshots` создаёт PNG каждой карты в
`build/level-screenshots/{extra,classic,unused}/NNN.png`, сохраняя структуру
`assets/levels`. Сейчас получается 142 изображения, включая все скрытые карты.
Каждый запуск обновляет изображения из текущих `.map`, `background.bmp`,
`background.tsa` и набора 0 из `background.pal`; исходный ROM и cc65 не нужны.
Отрисовывается поле 13×13 метатайлов, без padding, базы, танков и HUD, которые
добавляются игровым кодом. PNG использует фиксированное RGB-приближение цветов
NES и целочисленное увеличение без сглаживания: по умолчанию ×2, 416×416 px.
`make level-screenshots LEVEL_SCALE=1` даёт исходные 208×208 px; доступны ×1…×8.

- `assets/chr/sprites.bmp` и `background.bmp` — две NES pattern table по 256
  тайлов. Это несжатые 8-bit indexed BMP 128×128; допустимы индексы 0–3.
- `assets/palettes/*.pal` — палитра спрайтов и девять наборов фоновой палитры;
  значения записаны как шестнадцатеричные индексы цветов NES `00`–`3F`.
- `assets/metatiles/background.tsa` — 16 блоков 2×2: номер подпалитры и четыре
  индекса фоновых CHR-тайлов. Номер строки совпадает со значением в карте.
- `assets/levels/extra/*.map` — 105 последовательных карт Tank 1990 из
  `$8000-$A552` в PRG0; текущий runtime-загрузчик не использует их как каталог
  игровых этапов.
- `assets/levels/classic/*.map` — 36 карт фактического runtime-каталога.
- `assets/levels/unused/001.map` — неиспользуемая карта из `$A800`, сохранённая
  в ROM без обнаруженной ссылки; вынесена отдельно для редактирования и анализа.

Искомые 70 скрытых карт уже содержатся в `extra/002.map`, `extra/037.map`–
`extra/105.map`. Первая — вариант `classic/002`
с двумя изменёнными TSA-блоками, остальные 69 — другие карты. Вместе с отдельной
картой `$A800` получается 71 скрытая геометрия. Остальные 35 записей PRG0
побайтово повторяют `classic`; всего в ROM 142 физические записи и 107 различных
карт. Экспорт `build/hidden-levels/` удобен для просмотра, редактировать нужно
исходные assets по `index.csv`.

Карта состоит из 13 строк. В каждой строке первые 13 hex-значений задают
TSA-блоки игрового поля, а значение после `|` сохраняет неиспользуемый
ниббл-заполнитель оригинального формата. Конвертеры проверяют размеры и выполняют
обратное кодирование без потерь.

Штатные семь дескрипторов загрузчика указывают только на `classic`. Для номеров
за пределами длины выбранного поднабора загрузчик дополнительно сдвигает packed
поток на 0, 2 или 4 байта; это создаёт варианты карт, а не просто повторяет
каталог. Крайнее окно со сдвигом читает до четырёх байт из
`src/frontend_extensions.s`, сразу следующего за `ClassicLevels`. Точная формула и
ограничения описаны возле `LoadAndDrawStage`.

## Организация ASM

`src/header.s` содержит iNES-заголовок, `src/levels.s` подключает карты, а
`src/chr.s` — собранную графику. Исполняемый код разделён по игровым подсистемам:
цикл игры и экраны, PPU и OAM, ввод, счёт, танки, снаряды, усиления,
столкновения, звук и загрузка этапов. Небольшие смысловые модули подключаются
из файлов-владельцев через `.include` ровно в позиции оригинального ROM: это
сохраняет адреса и одновременно позволяет менять подсистему для ромхака без
поиска её частей в несвязанных крупных файлах. Точная карта приведена в
`docs/memory-map.md`.
Физические адреса областей ROM фиксирует `cfg/tank1990.cfg`.
Подтверждённая карта рабочей памяти и состояний аудиопотоков находится в
`src/ram.inc`, общие размеры пулов, маски и коды состояний — в `src/game.inc`.
Перегруженные временные байты получают локальные имена возле использующих их
процедур и не выдаются за глобальные игровые переменные.

Имена вида `Lxxxx` сохранены как адресные якоря оригинального ROM и не являются
публичным интерфейсом. Для нового кода следует использовать расположенные рядом
смысловые имена процедур, таблиц и переменных. Порядок и размер данных необходимо
сохранять, пока требуется побайтовая совместимость.

Практические замечания по созданию производных версий находятся в
`docs/hacking.md`, описание музыкального интерпретатора — в `docs/audio.md`.

Подробная независимая спецификация игры находится в
[`docs/spec/README.md`](docs/spec/README.md). Она описывает режимы, точный
порядок кадра, уровни, физику, ИИ, бонусы, счёт, графику, звук, эталонный
псевдокод и критерии совместимости; исходный ROM для реализации по ней не нужен.

`BC_SourceCode.asm` допускается использовать только как справочник при
проверке спорной интерпретации. Имена и комментарии из него в этот проект не
переносятся.
